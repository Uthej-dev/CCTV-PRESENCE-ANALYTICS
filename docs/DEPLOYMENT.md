# Deployment

Target setup:

```text
Browser ──HTTPS──▶ Vercel (React static build)
   │
   └──HTTPS (REST + MJPEG)──▶ Render / Railway / VM (FastAPI + YOLO, Docker)
                                      │
                                      ▼
                               MongoDB Atlas
```

The order matters: **database → backend → frontend → update backend CORS**.

---

## 1. MongoDB Atlas

1. Create a free account at <https://www.mongodb.com/cloud/atlas> and create an **M0 (free)** cluster.
2. **Database Access** → *Add New Database User* → username + generated password
   (role: *Read and write to any database*).
3. **Network Access** → *Add IP Address* → `0.0.0.0/0`
   (Render/Railway don't have fixed outbound IPs on the cheaper plans; the password protects the DB).
4. **Connect** → *Drivers* → copy the connection string, e.g.

   ```text
   mongodb+srv://cctv:<password>@cluster0.abcd123.mongodb.net/?retryWrites=true&w=majority
   ```

   Replace `<password>`. URL-encode special characters in the password (`@` → `%40`, etc.).

Indexes (including the 90-day TTL on occupancy samples) are created automatically when the API starts.

---

## 2. Backend

### Memory requirement

PyTorch + YOLO11n + OpenCV use roughly **0.8–1.2 GB RAM** with one camera running. Free/512 MB
instances are killed for running out of memory. Pick one of:

| Option | Cost | Notes |
|---|---|---|
| **Render** Standard (2 GB) | paid | Easiest: `render.yaml` blueprint included |
| **Railway** | usage-based | Deploy from repo, set root to `backend/` |
| **VM** (Oracle Cloud free ARM 4 CPU / 24 GB, Hetzner, DigitalOcean 2 GB) | free–low | Most headroom; run with Docker |

Inference runs on CPU in the cloud (~25–40 ms/frame for YOLO11n), so `PROCESS_FPS=8` and
`MAX_RUNNING_CAMERAS=2` are sensible defaults on 1–2 vCPUs.

### Option A: Render (blueprint)

1. Push the repository to GitHub.
2. Render Dashboard → **New → Blueprint** → select the repo. It reads `render.yaml`.
3. Fill in the prompted variables:
   - `MONGODB_URI` = Atlas connection string from step 1
   - `CORS_ORIGINS` = leave a placeholder for now (e.g. `https://example.com`), updated in step 4
4. Deploy. The first build takes several minutes (PyTorch). When it's live, open
   `https://<service>.onrender.com/health`. You should see `"database": "connected"`.

`JWT_SECRET` is generated by Render. The app **refuses to start** in production with a short or default
secret.

### Option B: any Docker host / VM

```bash
git clone <your repo> && cd <repo>/backend
docker build -t cctv-api .
docker run -d --name cctv-api --restart unless-stopped -p 8000:8000 \
  -e ENVIRONMENT=production \
  -e MONGODB_URI='mongodb+srv://...' \
  -e JWT_SECRET="$(openssl rand -hex 32)" \
  -e CORS_ORIGINS='https://your-app.vercel.app' \
  -e YOLO_DEVICE=cpu -e PROCESS_FPS=8 \
  -v cctv-data:/app/data \
  cctv-api
```

Put it behind HTTPS (Caddy is the simplest: `your-domain { reverse_proxy localhost:8000 }`).
The frontend on Vercel is HTTPS, and browsers block calls from an HTTPS page to an HTTP API.

### Important: one process

Run **one** uvicorn process per backend instance (the Dockerfile does). Camera workers live in
that process's memory; `--workers 4` would create four independent managers that don't see each other.

## 3. Frontend (Vercel)

1. Vercel → **Add New → Project** → import the repo.
2. **Root Directory**: `frontend` (framework preset: Vite is detected).
3. **Environment Variables**: `VITE_API_URL` = your backend URL, e.g. `https://cctv-analytics-api.onrender.com`
   (no trailing slash).
4. Deploy. `vercel.json` rewrites all paths to `index.html` so deep links like `/cameras/123` work.

Vite inlines `VITE_API_URL` **at build time**: after changing it, redeploy.

---

## 4. Connect them

Set the backend's `CORS_ORIGINS` to the Vercel URL (comma-separate several, e.g. a custom domain):

```text
CORS_ORIGINS=https://cctv-analytics.vercel.app,https://cctv.yourdomain.com
```

Redeploy or restart the backend.

---

## 5. Smoke test

1. Open the Vercel URL → **Create account**.
2. **Cameras → Add camera** → source *Video file* → pick `people-detection.mp4`
   (downloaded on first start) or **Upload…** your own clip.
3. **Start detection** → **Live monitoring** shows boxes and IDs within a few seconds.
4. After a minute, **Dashboard** and **Entry / exit history** show data.

Optional: seed demo history so the charts are populated (run once, inside the backend container/shell):

```bash
python -m scripts.seed_demo --email you@example.com --days 14
```

The data is synthetic and clearly labeled (`Demo Lobby (synthetic)`). Remove it with `--clear`.

## Troubleshooting

| Symptom | Cause / fix |
|---|---|
| Frontend shows "Cannot reach the server" | Wrong `VITE_API_URL` (redeploy after changing it), or backend asleep/crashed |
| Browser console: CORS error | `CORS_ORIGINS` doesn't exactly match the frontend origin (scheme + host, no trailing slash) |
| `/health` → `database: unreachable` | Atlas IP access list, wrong password, or unencoded special characters in the URI |
| Backend restarts when a camera starts | Out of memory: use an instance with ≥ 2 GB RAM |
| Camera status `error`: "Could not open rtsp source" | The camera must be reachable **from the server**, not just from your laptop |
| Webcam source fails in the cloud | Expected: a webcam source means a camera attached to the *server* machine |
| Uploaded videos / recordings disappear after deploy | No persistent disk: mount one at `/app/data` (render.yaml does) |
| `Permission denied` writing to `/app/data` | The mounted disk is owned by root while the app runs as `appuser`: `chown` the mount once, or remove `USER appuser` from the Dockerfile on that host |
| Disk filling up | Recordings are kept `RECORDING_RETENTION_DAYS` (default 7, roughly 35 MB per hour of activity per camera); lower it, or raise `RECORDING_CRF` for smaller files |
